# Aesthetic rules

*Change log: [AESTHETIC-RULES-CHANGELOG.md](changelog/AESTHETIC-RULES-CHANGELOG.md)*

The rules every screen of *Who Knows, Who Acts?* follows: the facilitator manager and the player screens alike. They keep the interface **intentional and consistent**: a calm terminal (TUI) look with Catppuccin colours (plus a high-contrast theme), JetBrains Mono, Iconoir icons and CRT-style animations. When you add UI, follow these rules and go through the [checklist](#11-checklist-for-new-ui).

Implementation: `apps/client/src/ui/`. That folder holds the tokens, base stylesheet, animation layer (`crt.css`) and components. Components must use the semantic tokens, components and icons defined there, **never raw colours, ad-hoc fonts or direct icon imports**.

## 1. Principles

1. **A terminal, not a web page.** One monospace font. Square corners. Box-drawn panel frames with the title in the border. Buttons read `[ LABEL ]`, statuses read `[ONLINE]`, and progress shows as `▰▰▱▱▱ 2/5`.
2. **The order of events is always visible.** Every multi-step flow shows where you are, what is done and what comes next (§ 8). The facilitator never has to wonder "what now?".
3. **One primary action per view.** Exactly one filled blue (`--primary`) button per screen or popup: the thing you most likely do next. Everything else is secondary.
4. **Colour carries meaning, never decoration.** Each accent has a reserved meaning (§ 2.2). If something is green, it is live or OK.
5. **Calm by default.** Effects are subtle, never block reading, and switch off completely for reduced-motion users (§ 9).
6. **Research data is never styled away.** Scores are always written as numbers, never shown by colour alone. The knowledge-type colours and the hatched / filled patterns mean the same in every theme, screen and legend (§ 2.2).

## 2. Colour

### 2.1 Themes and tokens

Three themes: the Catppuccin flavours **Latte** (light) and **Mocha** (dark), and **High contrast**. Components use **only** these semantic tokens, as CSS variables, e.g. `var(--primary)`.

- In **Mocha**, the accents are Catppuccin's own.
- In **Latte**, the accents are darkened by the smallest step that reaches WCAG AA, because Latte's pastels are too light to read as text on a light background.
- **High contrast** is not a Catppuccin flavour: black background, white text and controls, saturated accents. Text and accent colours reach WCAG **AAA (≥ 7:1)**, a test checks this. Use it for participants or facilitators with low vision, bright rooms or poor projectors.

**Who picks the display settings:**

**Every screen picks its own display settings: colours, font, text size and animations. They are accessibility settings, never session settings.**

| Setting | Options (default first) |
| --- | --- |
| Colours | Latte · Mocha · High contrast (default: what the OS asks for) |
| Font | JetBrains Mono · OpenDyslexic · System font |
| Text size | Small · Large (all `--fs-*` tokens, icons and map labels about 25 % bigger) |
| Animations | On · Off |

- **Facilitator:** the *DISPLAY* segment in the status bar (or `D`) opens the settings popup. Single keys cycle each setting: `T` colours, `F` font, `S` text size, `A` animations.
- **Players:** a **DISPLAY** button in the bottom-right corner of every player screen opens a small panel with the same four settings. It stays reachable above popups, and `Esc` closes it.
- **Storage:** remembered per browser (`localStorage`). **Never sent to the server or logged**: a choice like High contrast or OpenDyslexic could hint at a visual impairment or dyslexia.
- **Default colours:** whatever the OS asks for. *More contrast* or forced colours → High contrast; otherwise dark → Mocha and light → Latte.
- Implementation: `ui/prefs.ts` (stores) and `ui/DisplaySettings.tsx` (the shared controls) set `data-theme`, `data-font`, `data-scale` and `data-crt` on `<html>`; `theme.css` maps them to tokens.

### 2.2 Reserved meanings

| Colour token | Means | Never use it for |
| --- | --- | --- |
| `--primary` (blue) | The primary action of a view, the current step, links | Status, decoration |
| `--live` (green) | LIVE indicator, success, connected, step done | Anything that is not "running / OK" |
| `--warn` (peach) | Needs attention: paused, idle, waiting, unfocused | Errors |
| `--danger` (red) | Destructive actions and errors, **always with an icon** | Emphasis |
| `--focus` (mauve) | Keyboard focus ring, the selected map square, the dashed outline of the sub-square a tool would act on | Anything else |
| `--review` / `--review-bg` (lavender) | The two **commit points** of setup: 06 review (everything is checked before the irreversible *Create session*) and 10 start onboarding (locks the seats and goes LIVE) | Anything else |
| `--k-a…d` (blue, amber, red, teal) | **Knowledge types** Ka–Kd: the outline of each sub-square on the map, its hatch (proposed) and fill (decided), timeline marks, and the swatch next to every K or P label. A power type uses the colour of its letter (Pa = Ka's blue). | Status, chrome, emphasis. Kc's red is a knowledge type, not danger: it never appears without its `Kc` / `Pc` label or on the map. |
| `--k-a-on…d-on` | Score numbers written on a filled (decided) sub-square | Anything else |
| `--seat-1…4` (peach, sapphire, green, mauve) | Identity of a seat, **always next to the seat number** | Status. Seat 3's green is an identity colour, not "OK". |

**Pattern = what happened, colour = which knowledge type.** Proposed is always **hatched**, decided always **filled**, on the map, in the timeline and in the `ActSwatch` next to quotas and buttons. Label text stays in text ink; the swatch (`LabelTag`, `ActSwatch` in `ui/components.tsx`) carries the colour, so a label is still readable for colour-blind users and in High contrast.

The knowledge-type colours come from a validated categorical palette: every pair was checked to stay apart for the common colour-vision deficiencies when the palette was chosen, and a test checks that every colour reaches 3:1 against the panel and that score numbers on a fill reach 4.5:1. The seat colours follow the hue structure of the Okabe–Ito colour-blind-safe palette (orange, sky blue, bluish green, purple), and seat badges always show the seat number as well.

## 3. Typography

**JetBrains Mono** (weights 400 and 700 only, no italics) everywhere by default, self-hosted via `@fontsource`, so it works offline on the session LAN. Ligatures are off; numbers align naturally in a monospace font.

The font is a display setting (§ 2.1). **OpenDyslexic** (also self-hosted) and the **System font** replace it through the `--font` token. Components therefore never name a font; they inherit `--font`. With OpenDyslexic, UPPERCASE and letter spacing are switched off everywhere, as dyslexia style guides advise. Printables (key sheet, takedown cards) always use JetBrains Mono.

The sizes below are the **Small** (default) text size. **Large** steps every token up: 14 / 15 / 16 / 19 / 25 px. Use the `--fs-*` tokens, never fixed pixel sizes, so both sizes work.

| Step | Size | Use |
| --- | --- | --- |
| micro | 11 px | Status tags, table headers, key hints |
| meta | 12 px | Labels, secondary text, buttons, tables, panel titles |
| body | 13 px | Running text, inputs |
| title | 15 px | Section headings (`h2`), popup titles, UPPERCASE, tracked 0.08–0.1em |
| heading | 20 px | Page headings (`h1`), UPPERCASE |
| display | 64–140 px | Client number on the waiting screen only |

- UPPERCASE plus letter spacing is used for **structure**: titles, tabs, buttons, tags, table headers. It is never used for running text, consent text or the briefing.
- Bold (700) is used for titles, buttons, current step and key values. Nothing else.

## 4. Spacing and shape

- **8 px grid:** `--s1` 4 · `--s2` 8 · `--s3` 12 · `--s4` 16 · `--s5` 24. No other gaps.
- **Corners:** `--radius` 2 px everywhere, except seat dots (round).
- **Lines:** solid 1 px frames (`--frame`) for panels and popups. Dashed 1 px lines separate rows and sub-sections. Control borders use `--control` (≥ 3:1).
- **Depth:** the page background (`--bg`) sits behind panels (`--panel`). Inputs, table headers and the status bar are sunken (`--sunken`). Only popups and toasts have a shadow.

## 5. Icons

**Iconoir only**, through `<Icon name="…"/>` (`apps/client/src/ui/Icon.tsx`). Each concept has exactly one icon. A unit test checks that the table and the implementation match.

- **Stroke** 1.5, colour `currentColor`, so icons take the colour of their text.
- **Sizes:** 16 px inline and in normal buttons, 20 px in large buttons and popup titles, 24 px for display use. No other sizes.
- **Icon plus text** by default. Icon-only buttons are allowed only in tight toolbars (map zoom, close ✕). They must have a `title`, which becomes both the `aria-label` and the styled tooltip.
- Destructive and warning actions always show their icon (`warning`, `erase`, `stop`, `withdraw`), so meaning never depends on colour alone.

## 6. Panels

- Every content block is a `Panel`: a 1 px frame with an **UPPERCASE title inset into the top border** (`─ SEATS`), an optional icon, and optional actions inset at the top right.
- **One level of nesting at most.** A panel inside a popup or a panel uses `nested`.
- Panels are arranged in a grid with `--s3` gaps. Order them by **importance and order of use**: the next action first, then state (seats), then monitoring (maps), then logs.
- Empty panels say why they are empty and what to do (e.g. "No clients yet. Open the player URL on each PC.").

## 7. Popups, confirmations and toasts

**Use a popup for:**

1. short multi-step flows that interrupt the work (wrap-up)
2. confirming destructive or irreversible actions
3. state changes that block the screen for players (paused, round break, end)
4. help

Use a panel, not a popup, for anything that should stay visible while working. **Long step-by-step flows (session setup) are an accordion of collapsible panels, not popups** (§ 8).

**Structure** (`Popup`):

- **Title bar:** icon, UPPERCASE title, `STEP nn/NN` in multi-step flows, and ✕.
- **Stepper strip** in multi-step flows.
- **Body**, which scrolls.
- **Footer:** secondary actions on the **left** (Back, Cancel), the primary action on the **right**. Key hints go on the buttons (`Enter`, `Esc`).

**Behaviour:**

- **Only one popup at a time.** Never stack popups. A confirmation replaces any open popup for its duration.
- Focus moves into the popup and is trapped there. It returns to where it was afterwards.
- **Enter** runs the primary action, except in destructive popups.
- **Esc** closes the popup. Esc never confirms anything; use **Back** to go to the previous step.
- Global single-key shortcuts are paused while a popup is open.

**Confirmations** (`useConfirm()`):

- Needed for: end round, end game, abort, withdraw, close session, revoke, disabling consent.
- **Irreversible** actions (erasure) also require **typing** the participant code.
- Destructive confirmations use the danger tone and a `danger-solid` confirm button. Enter does nothing there, so the user must click or tab to the button.

**Hover helpers** (`<Button tip="…">`, one global tooltip layer in `ui/Tooltip.tsx`):

- They say what a button does and what it touches (e.g. "Write a pseudonymised export … with participant codes"). Every button whose effect is not obvious from its label has one; so do map sub-squares (name, score or "score unknown to you", marks), timeline marks and label swatches.
- On a `Button`, `tip` falls back to `title`. Raw elements use `data-tip`; avoid the native `title` attribute, which shows a second, unstyled tooltip.
- They appear on hover after 350 ms and immediately on keyboard focus. Screen readers get the same text as the button's description.
- They are never the only place for information that is needed to act safely; confirmations say it again.

**Toasts** (bottom right, above the status bar):

- One at a time, prefixed `[ OK ]`, `[WARN]`, `[FAIL]` or `[INFO]`.
- They auto-dismiss after 3 s (errors after 6 s).
- Use them for the result of an action. Never use them for information the user must act on; that goes in a panel or popup.

## 8. Order of events and wayfinding

- **Facilitator tabs, in order of use:** `[1] SETUP | LIVE`, `[2] REPLAY`, `[3] DATABASE`.
  - The first tab is **one tab with two faces**. It reads **SETUP** until "Start onboarding", then flips to **LIVE**.
  - A green **`● LIVE S-…`** indicator in the top bar shows that a session is running; clicking it always leads back to it.
- **Setup:** ten steps as a **vertical accordion** of collapsible panels (`01 SCENARIO`, `02 ROUNDS`, … `10 START`). Exactly one step, the current one, is expanded, with Back and Next/Create/Start in its footer. *Next* collapses it into a one-line summary and expands the next step below.
  - The headers are the stepper: glyph, number, title and the step's summary, so the whole setup can be read at a glance.
  - Finished steps can be reopened by clicking their header. Steps 01–06 lock (■) once the session is created.
  - A blue **wayfinder bar** is pinned to the top of the page while you scroll. It shows `▶ STEP nn/10 · TITLE`, the keys, and a strip of all ten steps (`✓ 01 Scenario`, `▶ 03 Players`, `· 04 Onboarding`, …); click a finished step to reopen it. Steps scrolled into view stop below the bar.
  - The two commit points, **06 REVIEW & CREATE** and **10 START ONBOARDING**, have their own colour (`--review`, § 2.2).
  - `Enter` in a step moves to the next one; `N` jumps to the current step. The draft survives reloads.
- **Live:** a lifecycle stepper `ONBOARDING → ROUND 1 → … → ROUND N → WRAP-UP`, plus a **NEXT** panel with the single next action and its key (`N`).
- **Players:** a stepper `CONSENT → ABOUT YOU → BRIEFING → READY` during onboarding, and a status line (round, quotas, timer) during the game.
- **Stepper glyphs:** `✓` done · `▶` current · `·` upcoming · `■` locked · `–` skipped (a step a simulated session does not need: 04 onboarding and 09 key sheet; shown muted, not green, with a dotted border in the wayfinder).
- **Simulated sessions** are marked, never coloured: a neutral **`[SIMULATION]`** tag with the *simulation* icon (flask) in the top bar, the setup wayfinder and the LIVE session panel, and the *agent* icon (chip) wherever a seat is played by an agent. No accent colour is reserved for them (§ 2.2), so green still only means "running / OK".
- **Fake players** (test clients in a real session) are marked the same way: a neutral **`[FAKE]`** tag with the *fake* icon (test tube) on their seat, in the mirrors and the bind step, **`[FAKE PLAYERS ×N]`** in the top bar, and `fake ×N` on the session in DATABASE.
- **Sub-tabs** inside a page (DATABASE: *Participants* | *Simulations*) use the same `tab` style as the top bar, in a `subtabs` row under it.

## 9. Motion and animations

There are **no static CRT effects** (no scanlines, no glow or bloom). The CRT character lives only in **animations**, all in `apps/client/src/ui/crt.css` and gated by the *Animations* switch (`data-crt="on"` on `<html>`).

| Animation | Where | Duration |
| --- | --- | --- |
| Screen switch (short vertical roll + brightness blip) | Changing tabs in the manager; changing screens on the player (waiting → consent → … → game → end) | 200 ms |
| Power-on / power-off (picture opens from / collapses into a line) | Popups opening / closing | 180 / 130 ms |
| Typed-in title | Popup titles | 320 ms |
| Signal lost (flicker, then dimmed) | Whole screen when the server connection drops | 420 ms, then stays dimmed |
| Signal back (power-on) | Whole screen when the connection returns | 260 ms |
| Status flicker | `[ONLINE]` / `[OFFLINE]` tags and the status bar whenever a connection state changes | 320 ms |

Ordinary UI motion that is **not** part of the CRT style: an accordion step fades in when it expands (160 ms).

**Rules:**

- **Never animate data.** Maps, highlights, quotas, tables and timers update instantly, especially during a round. Only chrome animates.
- Nothing loops: no blinking cursors, pulsing dots or flicker except the one-off state changes above. The block cursor `█` is static.
- **`prefers-reduced-motion: reduce` switches off every animation.**
- Otherwise animations are a display setting of each screen (§ 2.1): the facilitator toggles them with `A` or the DISPLAY popup, each player in their DISPLAY panel. They are not recorded.

## 10. Keyboard

TUI-style single keys. They are ignored while typing in a field, while a popup is open, and when a modifier key is held. `?` shows the full list in the facilitator.

| Key | Facilitator | Player |
| --- | --- | --- |
| `1` `2` `3` | SETUP/LIVE, REPLAY, DATABASE | — |
| `N` | Do the NEXT action (setup: jump to the current step) | — |
| `P` | Pause / resume the round | Propose tool |
| `D` | Display settings popup | Decide tool |
| `T` / `F` / `S` / `A` | Next colour theme / next font / text size Small ↔ Large / animations on/off | — (DISPLAY button) |
| `?` | Shortcut help | — |
| `Enter` / `Esc` | Primary action (setup: next step) / close a popup | Confirm / cancel an action |

## 11. Checklist for new UI

- [ ] Uses only semantic tokens (`var(--…)`): no hex values or Catppuccin names in components.
- [ ] Every colour use matches its reserved meaning (§ 2.2). New pairs are added to `CONTRAST_PAIRS`, and the tests pass.
- [ ] Text uses the type-scale tokens (§ 3), no fixed pixel sizes and no named fonts; UPPERCASE only for structure.
- [ ] Spacing on the 8 px grid; 2 px corners.
- [ ] Icons only via `<Icon name>`. Any new concept is added to `ICON_TABLE` **and** `ICONS`.
- [ ] The content sits in a `Panel` with an UPPERCASE title; one primary action per view.
- [ ] Long step-by-step flow → accordion (§ 8); short interrupting flow → `Popup` with stepper and `STEP nn/NN`. Destructive → `useConfirm({ danger: true })`. Irreversible → `requireText`.
- [ ] Order of events visible: where am I, what is next?
- [ ] Works in Latte, Mocha **and** High contrast; in JetBrains Mono, OpenDyslexic **and** the system font; at Small **and** Large text; with animations on **and** off, and with reduced motion.
- [ ] Keyboard reachable; focus visible (`--focus`); icon-only buttons have a `title`.
- [ ] Buttons whose effect isn't obvious from the label (exports, printables, deletions, game actions) get a hover/focus helper: `<Button tip="…">`.
- [ ] Anything about a knowledge or power type uses its colour through `LabelTag` / `ActSwatch` (hatched = proposed, filled = decided), never a new colour.
- [ ] Run `npm run docs:generate` if tokens or icons changed.
